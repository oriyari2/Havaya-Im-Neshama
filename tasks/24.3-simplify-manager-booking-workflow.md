# Task 24.3: Simplify Manager Booking Workflow

## Status

Complete; validated, committed, and pushed.

## Design validation

`NEW` is the existing pending status. Customer requests use it and Dashboard
counts it as pending. The backend already supports the flow through separate
`CreateBookingCommand`, `AssignInstructorCommand`, and
`ChangeStatusCommand(CONFIRMED)` commands. No backend change is required.

## Implementation

- Manager creation offers an optional active Instructor selector.
- Instructor ID is never added to the Booking-create payload/event.
- After creation, `BookingsPresenter` delegates to the existing assignment
  Presenter, which loads the Booking Activity and calls its existing assignment.
- A `NEW` Booking exposes one “Assign Instructor and approve Booking” action.
  It uses the existing selector, assignment, returned version, and confirmation.
- If the pending Booking already has an assignment, the same action confirms it
  without adding a duplicate assignment.
- The standalone confirm control is hidden to avoid contradictory Manager UX.
- Customer creation remains `NEW` and unassigned.

Creation commits before optional assignment. If assignment fails, the Booking
remains visible and pending/unassigned for retry. Combined completion confirms
only after assignment succeeds.

Composite backend commands, transactional create+assign, new events/statuses,
notifications, assignment acceptance/rejection, and Task 25 are out of scope.

## Acceptance and validation

- Manager creation supports no Instructor or one active Instructor.
- Customer creation remains pending and unassigned.
- An unassigned `NEW` Booking can be assigned and approved through one action.
- An already-assigned `NEW` Booking can be approved without a duplicate assign.
- Presenter code remains Qt-free and Desktop code has no direct database access.
- Focused Desktop/backend tests, native Qt view tests, compileall, architecture
  scans, and `git diff --check` pass.
