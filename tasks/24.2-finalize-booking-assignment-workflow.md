# Task 24.2: Finalize Booking Assignment Workflow

## Status

Implemented and validated; commit and push close the refinement.

## Audit and decision

Assignment already exists and is complete. Managers use Booking Details to
select a Booking Activity and invoke `POST /bookings/{booking_id}/instructors`.
`AssignInstructorCommand` appends immutable `BookingInstructorAssigned`; removal
appends `BookingInstructorRemoved`. Projection updates and optimistic concurrency
remain unchanged. Instructors read only actively assigned Bookings.

No command, endpoint, or competing workflow was added. Discoverability was the
only gap: generic “link” wording did not explain the Activity selection required.

## Final lifecycle

1. Customer or Manager creates an unassigned Booking.
2. Customer sees their request; Manager sees all Bookings.
3. Manager reviews/manages the Booking.
4. In Booking Details, Manager selects the Booking Activity and chooses
   “Assign Instructor to selected Activity”.
5. The existing selector dispatches the existing assignment command once.
6. The Instructor sees the Booking on the next authorized work-list load/refresh.

Customers and Instructors never see assignment controls. Instructors cannot
create Bookings, select Customers, or self-assign. Assignment and Booking status
remain independent.

## Scope and out of scope

Only Manager labels/instruction text in the existing Booking Details assignment
group, affected tests, and documentation. Creation-time assignment,
notifications/realtime push, CQRS/Event Sourcing changes, approval/rejection,
and Task 25 are out of scope.
